# 都知事杯オープンデータ・ハッカソン提出スライド — デザインシステム

最終確認日: 2026-08-28
状態: 完了

このファイルは、提出スライドのトンマナを1か所で決めるための基準である。
スライドを直すときは、まずここを読み、ここを変えてから `build-deck.js` を直す。
1枚だけ例外の色や字送りを足さない。継ぎ足しで崩れたときに戻る先がなくなる。

## 1. 直した問題

改稿前のスライドは、2つのデザインが1つのファイルに同居していた。

- 明るい地（`#F4F7FB`）のスライドと暗い地のスライドが、根拠のない順序で交互に並んでいた（1暗・2明・3暗・4暗・5明・6暗・7明）
- 暗い地の値が3種類あった（`#0A1A2E` / `#080B18` / `#173A5E`）
- アクセントが2系統あった。青系（`#2F6EA8`）と、3・4枚目にだけ出る金（`#F2C97D`）・桃（`#EE8FA0`）
- 和文書体が2種類混在していた（Meiryo 189か所 / Noto Sans JP 106か所）
- 文字サイズが18段階、色が22種類あった
- どのスライドも下端30%前後が空き、16:9の下側を使えていなかった

個々のスライドは整っているのに全体が寄せ集めに見えたのは、この不統一が原因である。
色を1つずつ直しても直らない。基準を1組に決め、そこから組み直す。

## 2. 明暗の使い分け（これが唯一の規則）

**暗い地はこちらの語り。明るい面はプロダクトそのもの。**

- 全スライドの背景は `night` 1色。明るい背景のスライドは作らない
- 明色が出てよいのは端末画面の中だけ。スクリーンショットと録画がそれにあたる
- 結果として、夜の地の上で画面だけが光る。プロダクト名（ヨルケア）とも一致する

明暗が交互に来ていた元の構成は、この規則がなかったために起きている。

## 3. 配色

プロダクトの `tailwind.config.ts` が持つ `primary: #3d7ab8` を基準に、
暗い地の上で成立するよう明度を持ち上げた1組。

| 役割 | 値 | 使いどころ |
| --- | --- | --- |
| `night` | `#0E1E33` | 全スライドの背景。唯一の地の色 |
| `surface` | `#17293F` | カード面。端末のベゼル |
| `line` | `#26405C` | カードの罫（全周。片側だけの線は引かない） |
| `white` | `#FFFFFF` | 見出し、本文の一次 |
| `sec` | `#AFC3D9` | 本文の二次 |
| `muted` | `#8CA4BF` | 出典、注釈、フッター |
| `blue` | `#4E93D2` | ブランドのアクセント。ラベル、番号、リンク |
| `blueDeep` | `#3D7AB8` | プロダクトの primary。塗りチップの地 |
| `amber` | `#F2C97D` | 強調色。**1スライドにつき1回まで** |

配分は地が6〜7割、青が支え、金は一点だけ。3色を同じ重さで使わない。

`amber` を置く場所は意味で決める。飾りでは置かない。

- 3枚目 … 50.7%（就職後1年以内の離職）。この製品が解こうとしている数字だから
- 4枚目 … 見出しの「3つの特徴」
- 6枚目 … 端末内で完結するという設計判断
- 7枚目 … 現時点の担当範囲

桃（`#EE8FA0`）は廃止した。役割のない3つ目のアクセントだったため。

## 4. 書体

和文・欧文とも **Meiryo** の1種類。日本語環境の PowerPoint に標準で入っており、
審査員の端末で置き換わりにくい。すべての文字に明示指定しているため、
テーマ側のフォールバック（游ゴシック Light）は効かない。

字送りは7段階だけ。改稿前の18段階から絞った。

| 用途 | pt |
| --- | --- |
| 表紙のブランド名 | 54 |
| 数字（統計） | 50 |
| スライド見出し | 30 |
| カード見出し | 17 |
| 本文 | 13 |
| ラベル・チップ | 10〜11 |
| 出典・フッター | 9.5 |

行送りは本文 1.45 倍で統一する。

## 5. 格子

キャンバスは 13.333 × 7.5 インチ（16:9）。

| 位置 | 値 |
| --- | --- |
| 左右の余白 | 0.72 |
| 小見出し（eyebrow） | y = 0.44 |
| 見出し | y = 0.80 |
| 本文の上端 | y = 1.95 |
| フッター | y = 6.94 |
| 段間 | 0.32 |

- 3段組 … 各 3.751（統計、特徴）
- 2段組 … 6.75 と 4.823（58:42）
- 5枚目 … 端末 2.18 と、右の2×2（各 4.4815 × 2.11）

本文域は y = 1.95 から 6.6 前後まで使う。改稿前に余っていた下端は、
カードの高さを伸ばして埋めた。

## 6. 繰り返す要素（モチーフ）

**塗りチップ**（角丸・高さ 0.30）を、列挙とラベルのすべてに使う。

- 経歴のラベル（支援現場 / 企業人事 / 現在）
- Phase 1 / 2 / 3–5
- 手順の番号（1 / 2 / 3）と、実演の場面の番号（①〜④）
- データセットの種別（施設 / 調査）
- 特徴に対応する機能名

**カード**は面・全周の罫・角丸 0.09 で統一する。影は使わない（暗い地では効かない）。

やらないこと。

- 見出しの下の飾り線
- 帯・縦のストライプ・片側だけの罫
- 1枚だけの独自レイアウト

## 7. 読みやすさ

`night` を地としたときの本文色のコントラスト比。

- `white` … 16:1 前後
- `sec` … 9:1 前後
- `muted` … 6:1 前後（出典・フッターに限る）
- `blue` … 5:1 前後（ラベルなど大きめの字に限る）

会場のプロジェクタで明るく飛ぶことを見込み、本文は `sec` 以上を使う。
`muted` を本文に使わない。

## 9. 素材

- 表紙の端末画面 … アプリの実機スクリーンショット
- 実演の録画 … `record-demo.js` が実機の画面から収録し、860×1764 で書き出したもの（約23秒）
- 動画のポスター … 同じ録画の2.6秒地点。PDFで配ったときに残る絵
- 人物写真 … 正方形へ切り、900×900 へ縮小

原本の12.1MBは、録り直しと縮小で3.9MBになった。
