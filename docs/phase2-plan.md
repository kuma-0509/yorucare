# ヨルケア Phase 2 実行計画

策定日: 2026-07-25

状態: 確定

## 1. Phase 2 の目的

Phase 2 の目的は、機能数を増やすことではない。次のプロダクト仮説を、小さな投資から順に検証することである。

> 復職後の夜間・休日に心身の波が残る人が、1日1〜2分のセルフケア記録を、書けない日があっても再開でき、その記録を週次の振り返りや本人が選んだ相談の材料として使える。

検証対象は次の3点とする。

1. **記録負担**: スマートフォンで記録を短時間に完了できるか。
2. **再開可能性**: 毎日入力することを求めなくても、初回後や中断後に記録へ戻れるか。
3. **振り返り価値**: 蓄積した記録が、本人の週次の振り返りと次の小さな行動の整理に役立つか。

Phase 2 の利用指標は、アプリの使いやすさと継続利用を判断するためのものであり、症状改善や再休職予防などの医学的効能を示す指標ではない。PHQ-9、UWES-9、WHO-HPQ、PSQI 等を用いる実践研究の評価とは分けて扱う。

ヨルケアは診断・治療・処方、危機判定、24時間監視の代替ではない。ガイドラインの推奨を製品の医学的効能として主張しない。

## 2. 変えない前提

現在の5か月間プログラムでは、次を維持する。

- 本人のセルフケア記録は本人端末内に保存し、運営者、勤務先、支援機関へ自動送信しない。
- 匿名利用イベントは、入力本文や健康・服薬・面談内容を含めない。
- 匿名利用イベントを、研究参加者ID、氏名、連絡先、所属、研究アンケートと結合しない。
- 記録や週次まとめは初期状態を非共有とし、共有は本人の明示操作でのみ開始する。
- 未入力や中断を失敗として扱わず、連続記録だけを評価・強調しない。

アカウント、クラウド保存、外部AIへの記録送信、自動共有を導入する場合は、現在の参加説明とデータ保存仕様の範囲外となる。実装前に、同意、保存期間、削除、閲覧権限、安全管理、研究手続きへの影響を別途確認する。

## 3. 計測する指標

### 3.1 集計単位と共通定義

- 集計単位は匿名の `installId` とし、「人」ではなく「端末・ブラウザ単位」と明記する。
- `installId` を研究参加者IDや個人情報に対応づけない。
- `record_saved` の最初のサーバ受信日を Day 0 とする。
- 利用日は、サーバ受信時刻を日本時間の日付へ変換して数える。過去日の記録を後から編集しても、実際にアプリを使った受信日の活動として扱う。
- 同じ日に複数回保存しても、記録日数は1日と数える。
- 複数端末利用、ブラウザデータ削除、送信失敗は集計上の限界として併記する。

### 3.2 主要指標

| 指標 | 定義 | 判断したいこと |
| --- | --- | --- |
| 初週複数日記録率 | Day 0〜6 に2日以上 `record_saved` がある install の割合 | 初回保存だけで終わらず、もう一度使えるか |
| Week 2 継続率 | Day 7〜13 に1日以上 `record_saved` がある install の割合 | 2週目に戻れるか |
| Week 4 継続率 | Day 21〜27 に1日以上 `record_saved` がある install の割合 | 短期的な物珍しさを越えて使えるか |
| 週あたり記録日数 | 各週の重複を除いた `record_saved` 日数の中央値 | 毎日を強制せず、どの程度使われるか |
| 中断後再開率 | 7日以上記録がない期間の後に再度 `record_saved` がある install の割合 | 中断を失敗にしない設計が機能するか |

Day 7 の1日だけを見る指標は、利用日のずれに弱いため採用しない。7日幅の Week 2、Week 4 で判断する。

### 3.3 使いやすさの確認

健康情報を使わないダミーデータで、スマートフォンのタスクテストを行う。

- 5人中4人以上が、補助なしで基本記録を2分以内に保存できる。
- 5人中4人以上が、過去の記録から週の状態を振り返る場所へ到達できる。
- データ消失、意図しない共有、保存不能、相談導線へ到達できない問題を重大不具合とする。

人数が少ないため、利用率だけで結論を出さない。任意の終了後インタビューや一般化した利用者フィードバックを、数値の理由を理解する補足材料にする。個別の健康・服薬・面談内容は開発管理表や利用イベントに記録しない。

## 4. 投資判断ゲート

以下の数値は、医学的効果の基準や外部ベンチマークではなく、21名規模の初期検証で次の開発費を投じるかを揃えて判断するための内部基準である。

### Gate 0: 計測開始の条件

次のすべてを満たすまで、匿名イベントの本番永続化を開始しない。

- 許可イベントと各フィールドが一覧化され、自由記述や入力内容を受け付けない。
- 不正形式の拒否、重複対策、保存失敗時の扱いをテストできる。
- 利用者向け説明、オプトアウト方法、保存期間、削除手順、閲覧可能者が決まっている。
- 匿名利用イベントと、本人の記録、研究データを結合しないことが確認できる。
- 集計結果が少人数の個人を推測できる粒度で公開されない。

### Gate 1: 継続支援機能へ進む条件

判断対象は、Day 0 から4週間を観測できた install が15以上ある場合とする。15未満なら合否を出さず、計測期間または対象数を増やす。

| 判定 | 基準 | 次の判断 |
| --- | --- | --- |
| 継続投資 | 初週複数日記録率 60%以上、Week 2 継続率 50%以上、Week 4 継続率 35%以上、かつ基本記録の2分以内完了が5人中4人以上 | 週次まとめ、目標振り返り、自分メンテ等の価値検証を続ける |
| 改善して再検証 | 上記のいずれかが未達だが、重大不具合がなく、離脱理由に修正可能な入力負担や導線問題がある | 原因に対応する変更を1つだけ行い、同じ定義で再計測する |
| 保留・縮小 | 改善を1回行った後も Week 2 継続率が25%未満かつ Week 4 継続率が15%未満、または信頼・安全に関わる重大問題が残る | 高コスト機能を止め、対象・課題・提供方法を見直す |

### Gate 2: リマインドへ投資する条件

リマインドは、継続率が低いという理由だけでは実装しない。一般化したフィードバックで「忘れる」「始めるきっかけがない」が非継続理由の上位にあり、確認できた回答の30%以上に該当する場合に、通知ON/OFFと時刻設定だけの最小構成を検証する。

通知は初期状態をOFFとし、責める表現、症状を推測する表現、入力を強制する表現を使わない。小規模パイロットではA/Bテストによる効果断定を行わず、次の観測期間で同じ継続指標と通知停止理由を確認する。

### Gate 3: アカウント・クラウド保存へ投資する条件

次のすべてを満たす場合に限り、非同期 repository 境界、認証、クラウド保存の本実装へ進む。

1. Gate 1 の継続投資基準を満たす。
2. 端末変更・データ消失・複数端末利用が、3人以上または確認対象の15%以上で継続利用の阻害要因になっている。
3. 認証、アクセス制御、通信・保存時の保護、バックアップ、保存期間、本人による削除、運用者権限、インシデント対応、端末内データ移行の要件が文書化されている。
4. 現在の5か月間プログラムへ適用する場合は、参加説明、同意、研究・安全管理手続きへの影響確認が完了している。

条件を満たさない場合は、端末保存と本人操作によるバックアップを維持する。

### Gate 4: 共有へ投資する条件

次のすべてを満たす場合に限り、本人同意ベースの共有実装へ進む。

1. 週次まとめのタスクテストで、5人中4人以上が内容を理解し、共有前に対象期間・項目を確認できる。
2. 5人以上から、自分で選んだ相手へ共有したいという明示的な需要が確認できる。
3. 初期状態が非共有で、共有相手、項目、期間、有効期限、取り消し、閲覧権限を本人が選べる。
4. 勤務先や支援機関への自動共有、常時監視、本人の知らない二次利用を行わない。

最初の検証は、本人がその場で見せる画面または期限付き・閲覧専用のスナップショットとする。常時連携は対象外とする。

## 5. 実装優先順位

開発管理表の課題を確認する順番と、製品へ投入する順番は分ける。製品への投入は、次の優先順位とゲートに従う。

| 優先 | 実装・検証内容 | 完了条件 | 次へ進む条件 |
| --- | --- | --- | --- |
| P0 | 匿名イベントのデータ境界確定、永続化・集計、相談窓口導線、スマートフォン実機確認 | Gate 0を満たし、主要指標を同じ定義で再集計でき、重大不具合がない | 4週間の観測開始 |
| P1 | 3段階の入口による入力削減、翌日の小さな行動の振り返り、自分メンテ、週次まとめ、積み重ね表示 | ダミーデータのタスクテストと表示テストが通り、端末内で完結する | Gate 1 |
| P2 | リマインドの最小検証 | ON/OFF、時刻、責めない文面、停止手段が確認できる | Gate 2 |
| P3 | repository の非同期境界、アカウント、クラウド保存 | データ要件と移行・削除テストが通る | Gate 3 |
| P4 | 本人同意による週次まとめの共有 | 非共有初期値、範囲・期限・取消・閲覧権限のテストが通る | Gate 4 |

P1 内では、入力負担を下げる変更を最初に行う。週次まとめは、まず端末内の既存記録を定型ルールで整理し、空状態や中断を責めない表現を検証する。外部AIへ記録内容を送る実装は、Gate 3 と別途のデータ取扱い判断が完了するまで行わない。

自分メンテの提案は、診断、危機判定、治療提案ではなく、本人が選べる一般的なセルフケア案に限定する。

## 6. 直近の実行順

1. `POST /api/events` の許可イベントと保存項目を最小化し、永続ストア、重複対策、集計方法、保存期間、削除方法を決める。
2. Week 2 / Week 4 継続率を再現可能な集計として実装し、ダミーイベントで検証する。
3. 相談窓口導線とスマートフォン実機テストを完了する。
4. 入力負担を下げる変更から、P1 の機能を1つずつ実装・観測する。
5. Gate 1 の判定後に、リマインド、クラウド保存、共有へ進むかを個別に判断する。

複数の継続施策を同時に投入すると、どの変更が使いやすさに影響したか分からなくなる。P1以降は、原則として1変更ごとにタスクテスト、観測、判断を行う。

## 7. 意思決定記録

| 日付 | 決定 | 理由 |
| --- | --- | --- |
| 2026-07-25 | Phase 2 の中心を「記録の再開可能性と週次振り返り価値の検証」とする | 5か月間プログラムの1日1〜2分・中断可・週次振り返りという確定仕様に合わせるため |
| 2026-07-25 | 医学的効果の研究指標とアプリ利用指標を分離する | 利用継続を症状改善の根拠として扱わないため |
| 2026-07-25 | クラウド保存、外部AI、共有は段階的な投資ゲートの後に置く | 本人端末保存・非自動共有という現行仕様を守り、高コストかつ高リスクな変更を先行させないため |
| 2026-07-25 | 匿名利用イベントの永続ストアにNeon Postgresを採用する | Vercelのサーバレス環境から接続でき、重複防止、日次集計、Week 2 / Week 4集計を構造化して扱えるため |
