# AI機能の同意方針とツール設計の判断

決定日: 2026-08-01
状態: 集計値のみを外部へ出す方針で確定・集計ツール層を実装開始

## 1. 結論

AI機能が外部のLLM APIへ渡してよいのは、アプリ側で確定させた集計値・タグ・「できること」のタイトルだけとする。本人が書いたメモ本文（`note` / `warningNote` / `selfCareMemo`）は端末外へ出さない。

この方針は運用ルールではなく型で保証する。集計ツールの戻り値型にメモ本文のフィールドを置かないことで、後から誤って本文を渡す実装ができないようにする。

## 2. なぜ集計値のみか

- 報告先が支援者と医師であり、数値の誤りが本人の不利益に直結する。数える・並べる・絞るはすべてアプリ側の仕事とし、LLMには言語化だけをさせる。報告書は穴埋め方式で、数値の穴はアプリが埋める。
- メモ本文を送るには、既存の匿名利用イベントより一段重い個別同意UI、撤回導線、保存期間の設計が必要になる。集計値のみであれば報告書と「できること」提案は成立するため、実装を先に進められる。
- `docs/sharing-decision.md` は、15名の非商用フィードバック期間には特定の生成AI APIへの自動送信を本番実装しないと定めている。本方針はこれと矛盾しない。今回実装するのは送信を伴わない集計層であり、LLM呼び出しの本番投入は同文書のGateに従う。

## 3. 送ってよいもの・送らないもの

| 種別 | 外部LLMへ渡す | 理由 |
| --- | --- | --- |
| 集計値（平均、分布、日数、割合） | 渡す | アプリ側で確定済みで、本人を特定しない |
| `warningTags` | 渡す | 選択式の語で、本人が書いた文章ではない |
| 「できること」辞書のタイトル | 渡す | 提案を辞書の範囲内に限るために必要 |
| `moodLabels` | 渡す | 選択式のラベル |
| `note` / `warningNote` / `selfCareMemo` | 渡さない | 本人が書いた本文。型に持たせない |
| 日付そのもの | 期間の端だけ渡す | 日単位の全履歴は再識別性を上げるため、集計に畳む |

本人が自分の判断で本文を外部AIへ渡したい場合は、既存の共有テキスト機能（`src/lib/ai-share-text.ts`）を使う。こちらは本人が全文を確認したうえで自分で貼り付ける経路であり、アプリからの自動送信ではない。両者を混同しない。

## 4. `summarizePeriod` の戻り値で決めたこと

実装は `src/lib/ai/period-summary.ts`。

- **`recordedDays` を必ず返す。** 母数がないと、記録できないほどしんどかった期間がデータ上「平穏な期間」に見える。`daysInRange`（暦日数）と別に返す。
- **対象が0件のとき平均は `0` ではなく `null`。** `0` を返すとLLMが「気分が最低だった」と読む。「データがない」と「値が低い」を型で区別する。
- **項目ごとに母数を別々に返す。** `scoredDays` / `measuredDays` / `bedtimeDays` / `answeredDays` を個別に持つ。共通の `recordedDays` だけだと、LLMが誤った母数で割合を語る。
- **就寝時刻は平均ではなく中央値を、正午を基準とする窓で計算する。** 日をまたぐため単純平均が壊れる（23:00 と 01:00 の平均が 12:00 になる）。
- **割合は `donePercent` として0〜100の整数で返す。** 割り算をLLM側に残さない。
- **キー名に「効果」「effect」を使わない。** LLMは渡された言葉に引きずられ、相関を因果として断定する。事実だけを述べる名前にする。

## 5. 残りのツールで決めたこと

実装は `src/lib/ai/` 配下。集計は純関数として置き、保存先からの読み出しと `Result` 境界の受け渡しだけを `tools.ts` が担う。保存先が API に変わっても集計の実装は変えずに済む。

### 「期間内の生の記録」を返すツールは作らない

引き継ぎ時の設計にあった `getRecords(from, to)` は、そのまま実装すると本文を含む記録を外へ出すことになり、本方針を破る。代わりに本文を持たない `DailyView` を返す（`daily-view.ts`）。メモについては `hasMemo` として有無だけを返し、本文は渡さない。

記録がない日も `recorded: false` として返す。記録がある日だけを返すと、記録できないほどしんどかった日が期間そのものから消え、LLMが「その期間は何もなかった」と読む。

### 連続日数は未記録日で途切れさせる

`findStreaks`（`streaks.ts`）は期間内の全日を1日ずつ走査し、記録がない日は条件を満たさなかったものとして連続を切る。記録がない日を満たしたことにすると、記録できなかった期間が「好調が続いた期間」に化ける。連続が切れた理由を区別できるよう `unrecordedDays` も返す。

条件は自由な式ではなく閉じた集合（`StreakCondition`）にする。任意の条件を受け取れるようにすると、何を数えたのかを説明できない切り口が作られる。

### 頻度集計は並びを固定する

`listWarningTags` / `listSelfCare`（`frequency.ts`）は日数の降順、同数なら名前の昇順で並べる。並びが入力順で変わるとLLMの出力もぶれる。同じ日に同じ語が重複していても1日として数える。母数として `recordedDays` を返す。これがないと「3日に出た」が多いのか少ないのか判断できない。

### 実行日と非実行日の差分は、少ない日数では出さない

`relateSelfCareToMood`（`self-care-relation.ts`）はキー名に「効果」「effect」を使わず、`differenceInAverage` のように事実だけを述べる名前にする。片側の日数が `MIN_DAYS_FOR_COMPARISON`（3日）を下回る場合は差分を `null` にする。1日や2日の差を並べると、LLMも本人も意味のある傾向として読んでしまう。

非実行日の母数は「期間内のすべての日」ではなく「記録がある日」にする。記録がない日を非実行日に含めると、記録できなかった日が「セルフケアをしなかった日」として数えられる。

### 書き込み系のツールは用意しない

`tools.ts` に置くのは読み取りだけとする。LLMに保存・削除の手段を渡さず、下書きまでに留めて確定は本人のボタン操作にする。

### 毎回同梱するもの

直近7日の `DailyView` と「できること」辞書は `buildRecentContext()` でまとめて渡す。ほぼどの問いでも必要になるうえ量が小さく、都度ツールで取りに行かせると往復が増えるだけ。1か月以上の長期データと集計値は、必要なときだけツールで取りに行かせる。
