# ヨルケア開発フロー

## 標準フロー

コード変更を伴う開発は、原則として次の順で進める。

1. `AGENTS.md`、開発管理表、handoff、関係する実装・文書を確認する
2. 要件と影響範囲を整理する
3. 実装し、必要な回帰テストを追加する
4. `pnpm verify` を実行する
5. 実装とは別工程として差分をレビューする
6. 指摘を修正し、必須検証を再実行する
7. AIで確認できた項目とHuman Gateに残る項目を分けて報告する
8. 人間が実機、初見UX、サービス妥当性、公開URLを確認する
9. Human Gate承認後にのみ `main` へのマージを判断する

## 自動検証の役割

| 階層 | コマンド | 主な役割 |
| --- | --- | --- |
| 静的検証 | `pnpm lint` | ESLintによる問題検出 |
| unit / integration | `pnpm test` | 保存形式、移行、日付計算、入力規則、コンポーネント挙動など |
| production build | `pnpm build` | 型検査と本番ビルド |
| 必須検証一式 | `pnpm verify` | lint → test → buildをローカルとCIで共通実行 |
| mobile smoke E2E | `pnpm test:e2e` | 390×844のChromiumで初回表示、横あふれ、記録保存と一覧反映、主要タブ、console / page errorを確認 |
| 広範な開発用E2E | `pnpm test:checklist` | スマホチェックリストの機械的に確認可能な項目を広く補助確認 |

同じ契約を複数階層で無意味に重複させない。保存形式、移行、削除、日付境界などはVitestを中心とし、PR必須のE2Eは壊れたときの影響が大きい主要導線だけに絞る。`pnpm test:checklist` は広範で実行時間や環境依存が大きいため、毎回のPR必須検証には含めない。

## 差分レビュー

最低限、次を確認する。

- バグ、既存機能への回帰、データ消失・整合性
- localStorage等の既存データとの互換性、日付・時刻・JST境界
- エラー処理、アクセシビリティ、セキュリティ
- 個人情報・センシティブ情報、不要な複雑化・重複実装
- 不安を与える表現、医療行為・診断・治療と誤解される表現

重大または高優先度の問題を修正した後は、`pnpm verify` と影響する追加検証を再実行する。

## Human Gate

自動テストは、次の項目を確認済みとは扱わない。

- 初見参加者が補助なし・2分以内で基本記録を完了できるか
- 初見参加者が週のふりかえりへ到達できるか
- 分かりやすさ、安心感、文言の受け止め方、サービスとしての妥当性
- iPhone / Safari、Android / Chrome固有の表示と操作
- タップ、ソフトウェアキーボード、共有シート、ファイル操作、描画、音、発熱、パフォーマンス
- 公開URLが対象コミットを反映し、公開環境で最終動作するか

AI側の検証が完了してもHuman Gateが残る場合は、**「AI検証完了 / Human Gate待ち」**と報告する。Human Gate承認前は「本番確認済み」「リリース完了」と表現しない。
