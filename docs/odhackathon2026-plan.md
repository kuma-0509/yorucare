### 審査基準（First / Final 共通）

1. **データ活用** — オープンデータや民間データ等を有効活用しているか
2. **アイデア力** — 課題解消・期待実現へのアプローチが秀逸で、サービスとして成立しているか
3. **技術力** — 技術要素に合理性があり、完成度が高いか
4. **ソーシャルインパクト** — 都民のQOL向上に貢献し、実現可能性が高いか

### 収録時の制約（8/26-30）

- オンラインはZoom画面共有、現地はHDMI接続
- 収録枠は提出フォームから30分単位・早い者順で予約
- ハッカソン終了後から収録日までの資料ブラッシュアップは可

### 著作物の扱い（提出ガイド記載）

- 画面キャプチャはサイトの利用規約に準拠し、出典を明記。有料記事の引用は避ける
- Google Mapのキャプチャ利用は可。ただし**ロゴ・帰属表示の隠蔽や改変は不可**
- 『いらすとや』は1資料あたり最大20個まで
- **BGM等の音源は使用を避ける**。静かな場所で収録する
- 音声合成は、身体・体調上の合理的理由がある場合のみ。時短目的の利用は不可
- AI生成の加工素材は元素材の利用規約の範囲内。不明なら使用しない

## 1. 現状のギャップ

**ヨルケアは現時点でオープンデータを一切利用していない。** リポジトリ全体を検索しても、オープンデータの取得・参照・出典表記のいずれも存在しない。

これは二重の問題になる。

1. **提出要件を満たさない。** オープンデータの登録は最低1件が必須で、未登録では提出そのものが成立しない
2. **審査基準の筆頭を落とす。** 「データ活用」は5項目の1番目であり、後付けで無関係なデータを1件貼るだけでは加点にならない

したがって本計画の中心は「オープンデータをヨルケアの中核機能として、無理なく組み込むこと」に置く。

## 2. 勝ち筋 — 「支援の空白」をオープンデータで可視化する

ヨルケアの事業仮説は `docs/evidence/vha2026-entry-summary.md` にある通り、**現在の支援体制が平日・日中を前提としており、心身が乱れやすい平日夜間・土日祝に機能する支援がほぼない**という構造的空白である。

この「空白」は、これまで主張として述べてきただけで、データで示してはいなかった。**東京都の相談窓口・支援機関のオープンデータ（所在地・受付日時）を突き合わせれば、空白は事実として描ける。**

### コンセプト

> 東京都の公的相談窓口の受付時間をオープンデータから集計し、「いま、ひらいている窓口」を提示する。同時に曜日×時間帯のヒートマップで、夜間・休日に窓口がほぼ閉じている事実を可視化する。

これが強いのは次の理由による。

- **課題提起そのものがオープンデータで裏付けられる。** 「土曜22時に都内で開いている窓口は◯件」という数字が、プロダクトの存在理由を1枚で説明する
- **既存機能の強化であり、後付けではない。** `docs/consultation-routing.md` で実装済みの相談先導線を、固定リストから公的データに基づく動的表示へ引き上げる形になる
- **審査基準を横断して効く。** データ活用（中核利用）／アイデア力（空白の発見）／ソーシャルインパクト（QOL・都民の到達性）／サービスデザイン（既存導線との一体化）に同時に効く
- **2分のプレゼンに収まる。** ヒートマップ1枚で課題、動作画面1枚で解決策が示せる

### 既存の設計方針は維持する

- 記録本文・選択値・端末IDは相談窓口へ送信しない（`docs/consultation-routing.md` 4節）
- 入力内容から危険度を推定しない
- 診断・治療・処方の代替ではないことを資料に明記する（`AGENTS.md`）

## 3. スコープ

### やること

1. 東京都オープンデータカタログから、相談窓口・支援機関のデータセットを選定する（精神保健福祉センター、保健所、障害者就労支援センター等）
2. データをビルド時に取得・正規化し、静的JSONとしてリポジトリへ同梱する（実行時APIに依存させない）
3. 「いま、ひらいている窓口」表示 — 現在時刻（JST）と受付時間を突き合わせる
4. 「支援の空白」ヒートマップ — 曜日×時間帯で開いている窓口数を集計して表示する
5. 既存の相談先ダイアログへ統合する
6. 出典表記とライセンス表示を画面とドキュメントへ入れる

### やらないこと

- 地図UIの新規実装（Google Mapの帰属表示リスクを避ける。必要なら地理院タイルまたはOpenStreetMapを検討し、それも間に合わなければ区市町村名によるリスト表示に留める）
- `DEVELOPMENT_BOARD.md` の未着手項目（目標機能、自分メンテ、LLM呼び出し、本棚演出の追加改善）。ハッカソン期間中は着手しない
- アカウント・クラウド保存（`docs/account-cloud-storage-decision.md` のGate未通過）

## 6. リスクと対処

| リスク | 影響 | 対処 |
| --- | --- | --- |
| **受付時間がオープンデータに構造化されていない** | コンセプトの根幹が崩れる | 8/10までに判断。代替として①所在地データによる「近くの窓口」表示＋受付時間は公式ページ参照、②医療・福祉施設データによる別角度の可視化、へ切り替える |
| 提出締切がハッカソン本番と同日 | 当日の不具合で提出不能になる | 8/21に一次提出、8/22に最終提出。23日を当てにしない |
| 収録枠が埋まる | 希望日時で収録できない | 一次提出を前倒しし、枠を先に押さえる |
| 2分に収まらない | 強制終了され、結論を言えずに終わる | 原稿を文字数で管理し、通し練習で計測する |
| Google Mapの帰属表示 | 規約違反の指摘を受ける | 地図UIを新規実装しない。使う場合はロゴ・帰属を改変しない |
| 医学的効能と受け取られる表現 | 信頼性を損なう | ガイドライン推奨を製品の効能として主張しない（`AGENTS.md`）。資料に「診断・治療・処方を行うものではない」を明記する |
| データのライセンス・出典漏れ | 減点・利用不可 | データセットごとにライセンスを記録し、画面と資料の両方に出典を表記する |
