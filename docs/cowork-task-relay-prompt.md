# Cowork タスクリレー進行プロンプト

yorucare の開発を、Cowork 上で「1チャット1タスク」ずつ順番に進めるための手順を定義する。各チャットはこのファイルと `docs/handoff/latest.md` だけを引き継ぎとして受け取り、他のチャットの会話履歴には依存しない。

## 各チャットで最初に読むもの

- `AGENTS.md`
- `docs/DEVELOPMENT_BOARD.md`
- `docs/phase2-plan.md`
- `docs/cowork-task-relay-prompt.md`（このファイル）
- `docs/handoff/latest.md`（前回チャットからの引き継ぎ。初回はまだ存在しない）

## 各チャットでやること

1. `docs/DEVELOPMENT_BOARD.md` の残タスク（進捗が `未着手`）を確認し、`docs/phase2-plan.md` の実装優先順位（P0〜P4、および各優先度内の順序）に照らして、次に着手すべきタスクが今回の依頼と一致しているか判断する。ずれている場合は着手前に理由を明らかにする。
2. 依頼された1件のタスクだけを実装する。他のタスクには手を出さない。着手前提が曖昧な場合（対象タスク名が未指定、設計判断が製品方針に関わる等）は、実装前に確認する。
3. `pnpm lint` / `pnpm test` / `pnpm build` を通す。ローカル環境の制約で `pnpm build` を最後まで実行できない場合は、代替検証（`tsc --noEmit` 等）の結果と、実行できなかった理由を引き継ぎに明記し、GitHub Actions（`.github/workflows/ci.yml`）での結果確認を次チャットに依頼する。
4. `docs/DEVELOPMENT_BOARD.md` の該当行を同じ作業内で更新する。進捗表記は管理表内の定義（`未着手`・`進行中`・`改善中`・`確認待ち`・`保留`・`後回し`・`判断済み`・`完了`）のみを使い、`完了` にした日だけ完了日を `YYYY-MM-DD` 形式で記載する。個人情報・利用者の健康や服薬、面談に関する情報は記載しない。
5. `docs/handoff/latest.md` を本ファイルの書式（下記）で作成・上書きする。
6. コミットして push する。コミットメッセージは変更内容が分かる日本語1行＋必要なら本文。
7. **PRを作った場合は、マージ前に自動レビューの指摘を確認する。** 指摘を1件ずつ「対応する」「対応しない」に振り分け、対応しないものは理由を引き継ぎに残す。CIが緑であることは、指摘が解消したことを意味しない。詳しくは下記「自動レビュー指摘の扱い」。
8. 最後に、次のチャットへそのまま貼れる引き継ぎプロンプトをコードブロックで出力する。書式は「各チャットでやること」の1〜8をそのまま再掲し、次に着手するタスク名を埋めたものとする。

## 自動レビュー指摘の扱い

PRには自動レビュー（`chatgpt-codex-connector`）が指摘を付ける。CIはこれを見ないので、緑のままマージすると指摘は未対応のまま残る。実際に5件目までで、PR #11 と #13 にまたがって5件が未対応のまま積み上がった。

マージ前に、必ず次を行う。

1. PRのレビューコメントを取得する（GitHub MCP の `pull_request_read` に `method: "get_review_comments"` を渡す）。
2. 指摘ごとに、自分で再現条件を確かめる。指摘文をそのまま信じない。誤検知なら、そう判断した根拠を書く。
3. 「対応する」ものは同じPRで直す。**そのPR自身が掲げた設計方針を満たせていないという指摘は、優先して直す。** 実装が意図どおりでない状態で方針だけが文書に残ると、後のチャットは文書を正しいものとして読む。
4. 「対応しない」ものは、理由を `docs/handoff/latest.md` の「引き継ぎ事項・注意点」に、PR番号・指摘の要約・見送りの理由の3点セットで書く。次のチャットが拾い直せる形にする。
5. 直したときは、修正前のコードでそのテストが実際に落ちることを確かめる。通ったままのテストは回帰を止められない。

指摘の対応で元の1タスクの範囲を越える修正が必要になった場合は、その修正だけを次のタスクとして引き継ぎに書き、無理に同じPRへ入れない。

## `docs/handoff/latest.md` の書式

```markdown
# Handoff

日付: YYYY-MM-DD
担当チャット: 何件目か（例: 1件目）

## 今回実装したタスク

- DEVELOPMENT_BOARD.md 該当行の課題名
- 実装内容の要約（3〜6行程度、設計判断の理由を含む）

## 変更ファイル

- 主要な変更ファイルの一覧（パスと役割を一言で）

## 検証結果

- pnpm lint: 結果
- pnpm test: 結果（テスト数など）
- pnpm build: 結果。ローカルで完走できなかった場合はその理由と代替検証内容、CI確認の要否を明記する

## 自動レビュー指摘

- PR番号と指摘件数。対応したもの／対応しなかったものを分け、対応しなかったものは理由を書く
- 指摘が0件だった場合も「0件」と書く（確認したこと自体を残す）

## 次のタスク候補

- DEVELOPMENT_BOARD.md と phase2-plan.md の優先順位に基づく次点候補（1件を明示し、理由を1〜2行）
- 判断が割れる場合は候補を並記し、次チャットで確認すべき点を書く

## 引き継ぎ事項・注意点

- 次のチャットが知っておくべき設計判断、保留にした論点、確認待ちの事項など
```

## 運用ルール

- タスクの選定は、原則として `docs/phase2-plan.md` 5節の優先順位（P0→P4、各優先度内の記載順）に従う。実装しやすさだけで順序を入れ替えない。
- 実機操作やヒアリングなど、チャット内のコーディング作業だけでは完了できないタスク（例: スマートフォン実機テストの実施そのもの）は、次点候補として明示するに留め、無理に「実装」扱いにしない。
- タスク名や設計方針が依頼文に明記されていない、または `docs/DEVELOPMENT_BOARD.md`・`docs/phase2-plan.md` の記載だけでは一意に決まらない場合は、実装を進める前にユーザーに確認する。
- `docs/DEVELOPMENT_BOARD.md` には個人情報、利用者が入力した健康・服薬・面談に関する情報、その他のセンシティブな情報、個人を特定できる情報を記載しない（`AGENTS.md` の定めに従う）。
- 自動レビューの指摘を未対応のままマージしない。対応しない判断をした場合も、理由を引き継ぎに残す（上記「自動レビュー指摘の扱い」）。前のチャットが残した未対応の指摘は、次のチャットが自分のタスクに入る前に確認し、そのタスクと同じ範囲で直せるものは直す。
