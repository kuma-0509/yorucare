# アカウント・クラウド保存の構成判断

決定日: 2026-07-26  
状態: 構成確定・本番実装は Gate 3 まで保留

## 1. 結論

現在の5か月間プログラムでは、本人の記録を端末内だけに保存し、本人操作によるJSONバックアップを維持する。アカウント、クラウド保存、本人の記録を受けるAPI、本人記録用DBはまだ作成・有効化しない。

### 15名の非商用フィードバック期間

継続投資の正式判定に向けて15名の協力者を募集し、15 install以上についてDay 0から4週間を観測できる状態を目標とする。この期間は非商用の検証として、現在の端末内保存と本人操作によるJSONバックアップを維持する。

- Vercel Pro、Neon Auth、本人記録用DB、AWS KMS、認証メールサービスは契約・有効化しない。
- 追加するアカウント・クラウド保存基盤の費用は0円とする。既存のドメインなど、この判断以前から発生している費用は含めない。
- 匿名利用状況の送信は初期OFF・任意同意のままとし、本人の記録本文、健康・服薬・面談に関する情報を送信しない。
- フィードバックは操作性について一般化した内容を集め、実際の記録本文を含むファイルや画面画像の提出を求めない。
- 15名から意見を得ただけではGate 1達成とせず、15 install以上でDay 0から4週間の観測が完了してから正式判定する。
- 商用利用へ移る場合、または現在の無料プランの利用条件・上限に適合しなくなる場合は、運用を継続する前に契約と費用を再評価する。

Gate 3を満たして本実装へ進む場合は、次の構成を採用する。

| 領域 | 採用する構成 |
| --- | --- |
| Webアプリ/API | 現在のNext.jsを継続し、本人記録APIはVercel Node.js FunctionsのSingapore（`sin1`）で実行する |
| 認証 | 本人記録専用NeonプロジェクトのNeon Auth。初期方式はメールのマジックリンクとし、パスワード、組織、SNSログインは有効にしない |
| セッション | Neon Authが発行するHttpOnly Cookieを使用し、クラウド有効化・全件削除・退会は直近10分以内の再認証を要求する |
| 本人記録DB | 匿名分析とは別のNeonプロジェクト、AWS Singapore、PostgreSQL 18を初期候補とする。導入時にサポート状況を再確認する |
| DB接続 | ブラウザからDBへ直接接続せず、Next.js APIだけが`@neondatabase/serverless`で接続する。Neon Data APIは採用しない |
| 認可 | APIで所有者を確認し、PostgreSQL RLSを第二の防御として全本人データテーブルへ適用する |
| 暗号化 | TLSとNeonの保存時暗号化に加え、記録本文をAWS KMSのデータキーによるAES-256-GCMでアプリケーション暗号化する |
| 同期方式 | 端末優先の保存と同期待ちキュー。クラウド反映前も端末保存の成否を明示し、複数端末競合を黙って上書きしない |
| バックアップ | Neonのスナップショットまたは時点復元を有効化し、復元試験と削除済みデータの再削除手順を運用に含める |

この判断は「将来の採用技術」を決めるものであり、現在の利用者にアカウント作成やクラウド送信を求める判断ではない。

## 2. Gate 3の現在地

`docs/phase2-plan.md` のGate 3は、次のすべてを満たした場合だけ本実装へ進むとしている。

| 条件 | 2026-07-26時点 | 判断 |
| --- | --- | --- |
| Gate 1の継続投資基準を満たす | 15名を募集する方針を決定。4週間の観測と判定は未完了 | 未達 |
| 端末変更・消失・複数端末が3人以上または15%以上の阻害要因 | 15名への一般化したフィードバックで需要を確認予定 | 未達 |
| 認証、認可、保護、バックアップ、保存期間、削除、権限、事故対応、移行要件を文書化 | 本文書で設計要件を確定 | 設計完了 |
| 現在のプログラムへの説明、同意、研究・安全管理手続きの影響確認 | 未完了 | 未達 |

したがって、現時点の判断は「構成を確定し、クラウド保存の本番実装は保留」である。条件未達のままDBや認証を先行導入しない。

## 3. データ境界

### 3.1 分離するデータ

| データ | 現在 | Gate 3後 | 結合してよい情報 |
| --- | --- | --- | --- |
| 本人のセルフケア記録 | 本人端末内 | 本人が明示的に有効化した場合だけ本人記録DB | 認証の不透明なユーザーIDだけ |
| 認証情報 | なし | 本人記録用Neonの`neon_auth`スキーマ | 本人記録の所有者ID |
| 匿名利用イベント | 匿名分析用Neon | 現行のまま | 匿名`installId`の不可逆化値だけ |
| 研究用アンケート | アプリ外の研究管理 | 現行のまま | 研究参加者IDだけ |
| プログラム運営情報 | アプリ外の運営管理 | 現行のまま | 運営上必要な情報だけ |

次の結合は禁止する。

- 匿名分析の`installId`と認証ユーザーID
- 本人記録と研究参加者ID、氏名、連絡先、所属、研究アンケート
- 本人記録と勤務先または支援機関の名簿
- 匿名分析DBと本人記録DBのSQL接続、外部キー、共通秘密鍵

本人記録用DBには、匿名分析用の`ANALYTICS_DATABASE_URL`を再利用せず、別プロジェクト、別DBロール、別の`USER_DATA_DATABASE_URL`を用いる。

### 3.2 クラウド保存の対象

クラウドへ保存する対象は、現行`Repository`が扱う次の2種類に限定する。

1. `DailyRecord`
2. `SelfCareItem`

端末の匿名分析同意、匿名`installId`、完了演出ログ、画面設定、バックアップ通知状態は同期しない。共有データ、外部AI入力、研究データもGate 3の対象外とする。

## 4. 本人同意と画面要件

- 初期状態は、アカウントなし・クラウド保存OFFとする。
- アカウント作成前に、保存対象、保存場所の国・地域、閲覧可能者、保存期間、削除、バックアップ残存期間、停止方法を短い要約と詳細画面で示す。
- アカウント作成と端末内データのアップロードを別の操作にする。アカウント作成だけで記録を送信しない。
- クラウド保存を有効化する直前に、アップロードする記録件数と「できること」の件数を示す。本文のプレビューを運営者向けログへ残さない。
- クラウド保存の同意と匿名分析の同意を別々に管理する。一方をONにしても他方を変更しない。
- OFFにすると新しい同期を止め、「クラウド上のデータも削除する」を本人が選べるようにする。
- 退会はクラウド上の本人データ削除を必須とし、「アカウントだけ残す」は提供しない。
- アプリ記録はリアルタイム監視されず、医療・緊急支援・危機判定の代替ではないことを維持する。

同意文面とプライバシー説明は、現在の5か月間プログラムへ適用する前に、研究・安全管理手続きへの影響を確認する。

## 5. 認証

### 5.1 採用

Neon Authを本人記録用Neonプロジェクトで有効化する。Neon Authは認証情報を同じNeonデータベースの専用スキーマへ保存し、HttpOnly CookieとRLS連携を提供する。初期認証は、本人がパスワードを新たに管理しなくてよいメールのマジックリンクを採用する。

初期構成では次を無効にする。

- パスワードログイン
- Google、Microsoft等のSNSログイン
- 組織・招待機能
- 管理者による利用者代理ログイン
- 認証イベントをマーケティングや匿名分析へ送るWebhook

パスキーは2026年7月時点で追加直後の機能であるため、初期方式にはせず、マジックリンクでの回復経路と実機利用性を保ったまま追加検証する。

### 5.2 必須要件

- マジックリンクは1回限り、短時間で失効し、要求回数をメールアドレスとIP単位で制限する。
- ログイン成功時に過去の同一利用者セッションを一覧表示・個別失効できるようにする。
- クラウド有効化、全件削除、退会、メール変更は直近10分以内の再認証を要求する。
- Cookieは`Secure`、`HttpOnly`、適切な`SameSite`を必須とする。
- メールアドレス、リンク用トークン、Cookie、JWTをアプリログへ出さない。
- 認証メール事業者の保存期間、再委託先、国外取扱い、削除条件を本番前に確認する。
- アカウント回復は認証メールだけで行い、運営者が本人記録の内容を尋ねて本人確認しない。

## 6. アクセス制御

### 6.1 API境界

ブラウザは次の順序で本人記録へアクセスする。

```text
ブラウザ
  -> Next.js本人記録API
    -> Neon Authセッション検証
      -> 入力スキーマ検証
        -> KMSによる暗号化・復号
          -> RLSを有効にした本人記録DB
```

本人記録APIは、リクエストCookieから検証したユーザーIDだけを所有者IDとして使う。本文、URL、フォームから所有者IDを受け取らない。

### 6.2 DB権限

- マイグレーション用DBロールと実行時DBロールを分離する。
- 実行時ロールには本人記録テーブルの必要な`SELECT`、`INSERT`、`UPDATE`、`DELETE`だけを与える。
- 全本人記録テーブルでRLSと`FORCE ROW LEVEL SECURITY`を有効にする。
- `SELECT`、`INSERT`、`UPDATE`、`DELETE`を別々のポリシーで検証する。
- 1リクエストのトランザクション内で、検証済みJWTクレームを設定してからSQLを実行する。
- 本番アプリへRLSを迂回できる所有者・管理者DB資格情報を渡さない。
- 運営者向けに本人記録を検索・一覧・閲覧する画面やAPIを作らない。

障害対応で本番アクセスが必要な場合は、時間制限、理由、二者承認、操作監査を必須にする。DBアクセス権とKMS復号権を同じ常設管理者へ付与しない。

## 7. 暗号化と鍵管理

### 7.1 通信・基盤

- ブラウザとVercel、VercelとNeon、VercelとAWS KMSの通信はTLSを必須とする。
- Neonの保存時暗号化とバックアップ暗号化を利用する。
- 本人記録本文は、DBへ渡す前にアプリケーションでも暗号化する。

### 7.2 アプリケーション暗号化

- AWS KMS `ap-southeast-1`の顧客管理対称鍵を1本用意し、自動ローテーションを有効にする。
- VercelのTeam issuer OIDCとAWS IAMロールを連携し、短時間資格情報でKMSを呼び出す。長期AWSアクセスキーはVercel環境変数へ保存しない。
- 利用者ごとに`GenerateDataKey`で256bitのデータ暗号鍵（DEK）を生成する。
- `DailyRecord`と`SelfCareItem`の内容を、DEKとAES-256-GCMで暗号化する。
- AADに、所有者ID、オブジェクト種別、オブジェクトID、スキーマ版、改訂番号を含める。
- DBには暗号文、nonce、アルゴリズム、鍵版、KMSで暗号化したDEKだけを保存する。
- 平文DEKは1リクエスト内だけで使用し、ログ、キャッシュ、DB、エラー監視へ出さない。
- KMSの実行時IAM権限は対象鍵の`GenerateDataKey`、`Decrypt`に限定し、暗号化コンテキストで用途を`yorucare-user-data`に制限する。
- KMS鍵の管理・削除権とアプリ実行権を分離する。

平文で保持する索引は、所有者ID、ランダムなオブジェクトID、記録対象日、改訂番号、スキーマ版、作成・更新時刻に限定する。気分、睡眠、服薬、しんどさのサイン、メモ、セルフケア名は暗号文に含める。

## 8. 保存期間、バックアップ、削除

### 8.1 保存期間

- クラウド保存が有効なアカウントは、本人が削除するまで保存する。
- 最終同期から365日間利用がない場合は、30日前に認証メール宛てへ予告し、再開がなければアカウントと本人記録を削除する。
- 保存期間は本番利用説明へ明記し、本人がアプリ内で最終同期日と削除予定を確認できるようにする。

### 8.2 本人操作による削除

- 1件削除は、端末とクラウドの対象行を削除し、再同期で復活させない削除版を記録する。
- クラウド全件削除は再認証後に実行し、記録、セルフケア、同期キュー、暗号化DEKを削除する。
- 退会は全セッション失効、本人記録削除、認証アカウント削除の順に行う。
- APIは削除要求を冪等にし、再実行しても成功として扱う。
- ライブDBからは24時間以内、通常は同一処理内で削除する。
- バックアップ内の暗号化済みデータは最長30日残る可能性を本人へ説明し、期限後に復元不能となることを運用確認する。

### 8.3 バックアップと復元

- 本番前に、利用プランの時点復元期間と内部バックアップ保持期間を契約・公式仕様で再確認する。
- 本人記録用DBのバックアップを匿名分析DBと混ぜない。
- 少なくとも四半期ごとにダミーデータで復元試験を行う。
- 復元は新しい隔離ブランチで検証し、削除済みアカウントが復活しないことを確認してから切り替える。
- 削除要求の記録を本人記録DBのバックアップとは別の最小限の運用記録として保持し、復元時に削除を再適用する。
- 運用記録には本文、メールアドレス、生のユーザーIDを保存せず、用途別HMAC値、要求時刻、完了時刻、結果だけを最大35日保持する。

## 9. 端末内データの移行と同期

### 9.1 初回移行

1. 既存の`parseExportPayload`と同じ上限・スキーマで端末データを検証する。
2. 移行前に本人がJSONバックアップを取得できる導線を表示する。
3. クラウド側が空であることを確認する。既存データがある場合は自動統合しない。
4. 対象件数とデータ境界を本人へ表示し、明示確認後だけアップロードする。
5. APIで全体を検証して暗号化し、単一トランザクションで保存する。
6. サーバ保存件数、改訂番号、チェックサムを照合してから同期済みとする。
7. 成功後も端末データを自動削除しない。

タイムアウト、通信断、容量超過、検証失敗が起きた場合は、端末データを維持して再実行可能にする。途中までのクラウド移行はトランザクションで残さない。

### 9.2 継続同期

- 端末保存の成功とクラウド反映の成功を別の状態として表示する。
- 端末保存後に同期キューへ積み、`pending`、`syncing`、`synced`、`conflict`、`error`を区別する。
- 各オブジェクトに単調増加する改訂番号を持たせ、古い改訂による上書きを`409 Conflict`で拒否する。
- 同じ日を複数端末で変更した場合は両版を一時保持し、内容を本人に比較して選んでもらう。最終更新時刻だけで黙って決めない。
- 削除にも改訂番号を持たせ、オフライン端末から古い内容が再作成されないようにする。
- 同期失敗を記録保存の失敗と誤表示せず、再送、JSONバックアップ、クラウド停止を選べるようにする。

## 10. ログ、監視、インシデント対応

- APIログはリクエストID、操作種別、HTTP状態、処理時間、件数だけに限定する。
- 本文、暗号文、メール、Cookie、JWT、所有者ID、記録対象日をログやエラー監視へ送らない。
- 認証失敗、RLS拒否、異常な大量取得、削除失敗、KMS復号失敗を個人内容なしで検知する。
- 本番権限の棚卸しを少なくとも四半期ごとに行う。
- 漏えい等が疑われる場合の封じ込め、鍵・資格情報の失効、影響範囲確認、本人通知・関係機関報告の判断責任者を本番前に決める。
- インシデント時も本人記録を診断、危機判定、常時監視へ転用しない。

## 11. 実装開始前の受入条件

次をすべて満たすまで、依存パッケージ追加、Neon Auth有効化、本人記録DB作成、本番環境変数設定、記録API公開を行わない。

- `docs/phase2-plan.md`のGate 3をすべて満たす
- 現在の5か月間プログラムへ適用する場合の説明・同意・研究・安全管理手続き確認が完了する
- Neon、Vercel、AWS、認証メール事業者の契約、保存国、再委託先、保持期間、削除条件を確認する
- 本人向けプライバシー説明と同意画面がレビュー済みである
- 運用者、権限管理者、インシデント責任者、削除要求担当者が決まっている
- Vercel `sin1`と本人記録用Neon/AWS KMSの費用を承認する

## 12. 本実装時の検証項目

本実装は、まずダミーデータ専用のPreview環境で行う。実データや現在の端末記録を使わない。

1. 未認証、期限切れ、改ざんCookieを拒否する。
2. 利用者Aの全CRUDを利用者Bから実行できないことを、APIとRLSの両方で確認する。
3. 所有者IDを本文から指定・変更できないことを確認する。
4. 正常な暗号化・復号、異なる鍵、AAD改ざん、nonce改ざん、鍵ローテーションをテストする。
5. ログとエラー監視に本文・認証情報が含まれないことを確認する。
6. 初回移行の成功、破損、上限超過、通信断、再実行、クラウド既存データとの競合をテストする。
7. 複数端末の更新競合と削除後の古い端末同期をテストする。
8. 1件削除、全件削除、クラウド停止、退会、再実行をテストする。
9. バックアップ復元後に削除済みデータを再適用できることを確認する。
10. スマートフォンでマジックリンク、再認証、同期状態、失敗時の復旧をタスクテストする。

## 13. 採用しない構成

| 構成 | 採用しない理由 |
| --- | --- |
| 匿名分析用Neonへの本人記録追加 | 匿名イベントと本人記録のデータ境界、資格情報、削除、権限を分離できない |
| ブラウザからNeon Data APIへ直接CRUD | 本人記録の入力検証、暗号化、レート制御、ログ抑制をNext.js APIへ集約するため |
| Vercel環境変数だけを使う単一共通暗号鍵 | 利用者別DEK、鍵の用途制限、監査、ローテーションを弱めるため |
| 独自パスワード認証 | パスワード保管、リセット、攻撃対策をアプリ側で持たないため |
| 最終更新時刻だけのLast Write Wins | 複数端末で本人の記録を気付かず失う可能性があるため |
| Gate 3前の先行クラウド実装 | 現行説明の範囲を変え、未確認の需要に高コスト・高リスクな投資を行うため |
