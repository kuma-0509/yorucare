# アカウント・クラウド保存の構成判断

決定日: 2026-07-26
改訂日: 2026-09-08（最小構成へ縮小、公式資料の確認結果を反映）
状態: 最小構成で実装可。本番の入口はフラグで閉じたまま

## 1. 結論

本人の記録を守る目的に限定した**クラウドバックアップと復元**だけを実装する。複数端末のリアルタイム同期は実装しない。

実装は行うが、公開の入口は初期OFF・本番画面から到達不可のまま据え置く。11節の受入条件を満たした時点でフラグを開ける。

| 領域 | 採用する構成 |
| --- | --- |
| 機能範囲 | クラウドへの自動バックアップと、別端末での復元だけ |
| Webアプリ/API | 現在のNext.jsを継続し、本人記録APIはVercel Node.js Functionsで実行する。実行リージョンは`vercel.json`の`regions`へSingapore（`sin1`）を1つだけ指定する |
| 認証 | 本人記録専用NeonプロジェクトのManaged Better Auth（旧Neon Auth）。方式はメールの6桁コード（Email OTP）だけとし、パスワード、組織、SNSログインは有効にしない。新規登録は無効にし、運営者が登録した参加者だけがログインできる状態にする |
| セッション | Managed Better Authが発行するHttpOnly Cookieを使用し、クラウド有効化・全件削除・退会は直近10分以内の再認証を要求する |
| 本人記録DB | 匿名分析とは別のNeonプロジェクト。ブラウザからDBへ直接接続せず、Next.js APIだけが`@neondatabase/serverless`で接続する |
| 保存単位 | 記録全体を1つのスナップショットとして保存する。既存の`buildExportPayload`が作る内容をそのまま暗号化し、1利用者1行で上書きする |
| 端末の扱い | 1アカウントにつき同期する端末は1台。新しい端末で復元するとそちらへ切り替わり、以前の端末は送信を停止して案内を表示する |
| 認可 | APIで所有者を確認し、PostgreSQL RLSを第二の防御として本人データテーブルへ適用する |
| 暗号化 | TLSとNeonの保存時暗号化に加え、スナップショットを利用者ごとのデータ鍵によるAES-256-GCMでアプリケーション暗号化する。親鍵はVercelのSensitive Environment Variablesに置く |
| 削除 | 本人操作による削除だけを実装する。未利用アカウントの自動削除は実装しない |
| 失敗時の扱い | 端末保存の成否とクラウド送信の成否を別に扱う。送信失敗は黙って再試行し、画面には最終預け日時だけを表示する |

### 1.1 この機能の成功の定義

継続率や有効化率では判定しない。この機能は利用を増やす機能ではなく、事故を防ぐ保険である。

- 主要な判定: 観測期間中に「機種変更・故障・ブラウザのデータ削除で記録を失った」という一般化した報告が0件であること。
- 補助的な判定: 復元が実際に使われた例が1件でも出た場合、この機能は元が取れたとみなす。

## 2. 2026-07-26版からの変更点

2026-07-26版は、複数端末同期を含むフル構成を前提としていた。協力者数と運用体制の実態に合わせ、投資額とリスクの両方を下げる方向へ縮小する。

| 項目 | 2026-07-26版 | 本改訂 | 理由 |
| --- | --- | --- | --- |
| 機能範囲 | 複数端末の継続同期 | バックアップと復元だけ | 同期の競合処理が実装量とデータ喪失リスクの大半を占めるため |
| 端末台数 | 複数端末を同時利用可 | 同期する端末は1台 | 「同じ日を2台で編集してどちらかが消える」問題を仕組みとして発生させないため |
| 保存単位 | `DailyRecord`と`SelfCareItem`を個別行で保存し改訂番号で競合検出 | 記録全体を1スナップショットで保存 | 1台運用ならサーバ側で1件ずつ区別する必要がなく、検証済みの`buildExportPayload`／`importBackup`を再利用できるため |
| 親鍵の管理 | AWS KMSの顧客管理鍵とVercel OIDC連携 | VercelのSensitive Environment Variables | 「DBの中身を見ても読めない」という保護はどちらでも同じで、KMSの利点（鍵使用履歴、鍵削除権の分離）は運用者が1名の段階では実質的に得られないため。AWSの契約・費用・連携設定を要さない |
| 保存期間 | 最終同期から365日で予告のうえ自動削除 | 本人操作の削除だけ。検証終了日に運用者が全件削除 | 自動削除は誤って本人の記録を消す取り返しのつかない不具合を抱えるため。数名規模では運用で確実に代替できる |
| ログイン方式 | メールのマジックリンク | メールの6桁コード（Email OTP） | リンク方式は自前のメール事業者が必須と公式に明記されており、事業者を1社増やすと保存国・再委託先・保持期間の確認が増えるため。パスワードを管理させない利点は同じ |

### 2.1 公式資料の確認結果（2026-09-08）

着手前に、採用構成の前提を公式資料で確認した。結果、追加費用は0円で足りる見込みであり、想定と違ったのはメール送信の1点だけである。

| 確認項目 | 結果 | 構成への影響 |
| --- | --- | --- |
| 製品名 | 「Neon Auth」はBetter Authを基盤とする **Managed Better Auth** へ改称。ドキュメントも`/docs/auth/`へ移動 | 本文書の名称と参照先を更新した |
| 提供状態 | **ベータ**。当四半期のGAを目標と記載 | 入口を閉じたまま実装するため許容する。公開前にGA状況を再確認する |
| 費用 | Freeプランで **60,000 MAUまで無料**。DBはFreeプランで100プロジェクト、プロジェクトあたり10ブランチ・0.5GBストレージ・100CU時間・5GB egress | 数名規模の検証では無料枠内。本人記録用に別プロジェクトを立てても追加費用は発生しない |
| ログイン方式 | マジックリンクとEmail OTPの両方を提供。管理画面のプラグイン設定で切り替える | リンク方式は下記の理由で採らず、Email OTPを採用する |
| メール送信 | 既定は共有SMTP（`auth@mail.myneon.app`）で開発・検証用の位置づけ。本番では自前のメール事業者を推奨し、**リンク方式を使う場合は自前事業者が必須** | ログイン方式をEmail OTPへ変更した。共有SMTPのまま検証を進め、公開前に到達性を確認する |
| 招待制 | 新規登録の可否を設定で切り替えられる。無効にすると既存の利用者だけがログインできる | 運営者が登録した参加者だけの閉じた検証にできる |
| リージョン | Neonは`aws-ap-southeast-1`（シンガポール）に対応。Managed Better AuthはAWSリージョンのみ対応 | 希望どおりシンガポールで構成できる |
| Vercel | Hobbyプランは実行リージョンを1つだけ選択可。既定は`iad1` | `vercel.json`の`regions`へ`sin1`を1つだけ指定する |
| 構成の制約 | フロントエンドとバックエンドが別デプロイの構成は未対応 | 本アプリはNext.js単体のため該当しない |

Gate 3 は `docs/phase2-plan.md` の定義どおりには満たしていない。本改訂は「作る範囲を最小に絞ることで投資額を下げ、ゲートの要求水準も同時に下げる」という判断である。この判断の前提は、8節の実装開始前の受入条件を満たすまで本番の入口を開けないことである。

## 3. データ境界

### 3.1 分離するデータ

| データ | 現在 | 有効化後 | 結合してよい情報 |
| --- | --- | --- | --- |
| 本人のセルフケア記録 | 本人端末内 | 本人が明示的に有効化した場合だけ本人記録DB | 認証の不透明なユーザーIDだけ |
| 認証情報 | なし | 本人記録用Neonの`neon_auth`スキーマ | 本人記録の所有者ID |
| 匿名利用イベント | 匿名分析用Neon | 現行のまま | 匿名`installId`の不可逆化値だけ |
| 研究用アンケート | アプリ外の研究管理 | 現行のまま | 研究参加者IDだけ |
| プログラム運営情報 | アプリ外の運営管理 | 現行のまま | 運営上必要な情報だけ |

次の結合は禁止する。

- 匿名分析の`installId`と認証ユーザーID
- 本人記録と研究参加者ID、氏名、連絡先、所属、研究アンケート
- 本人記録と勤務先または支援機関の名簿
- 匿名分析DBと本人記録DBのSQL接続、外部キー、共通秘密鍵

本人記録用DBには、匿名分析用の`ANALYTICS_DATABASE_URL`を再利用せず、別プロジェクト、別DBロール、別の`USER_DATA_DATABASE_URL`を用いる。

### 3.2 クラウド保存の対象

クラウドへ保存するのは、既存の`buildExportPayload`が返すスナップショットに含まれる次の内容に限定する。

1. `DailyRecord`
2. `SelfCareItem`
3. `NotToDoItem`
4. 復職日の設定

端末の匿名分析同意、匿名`installId`、完了演出ログ、画面設定、バックアップ通知状態は同期しない。共有データ、外部AI入力、研究データも対象外とする。

## 4. 本人同意と画面要件

- 初期状態は、アカウントなし・クラウド保存OFFとする。
- アカウント作成前に、保存対象、保存場所の国・地域、閲覧可能者、保存期間、削除、バックアップ残存期間、停止方法を短い要約と詳細画面で示す。
- アカウント作成と端末内データのアップロードを別の操作にする。アカウント作成だけで記録を送信しない。
- クラウド保存を有効化する直前に、アップロードする記録件数と「できること」「やらないこと」の件数を示す。本文のプレビューを運営者向けログへ残さない。
- クラウド保存の同意と匿名分析の同意を別々に管理する。一方をONにしても他方を変更しない。
- OFFにすると新しい送信を止め、「クラウド上のデータも削除する」を本人が選べるようにする。
- 退会はクラウド上の本人データ削除を必須とし、「アカウントだけ残す」は提供しない。
- アプリ記録はリアルタイム監視されず、医療・緊急支援・危機判定の代替ではないことを維持する。

同意文面とプライバシー説明は、現在の5か月間プログラムへ適用する前に、研究・安全管理手続きへの影響を確認する。

## 5. 認証

### 5.1 採用

Managed Better Auth（旧Neon Auth）を本人記録用Neonプロジェクトで有効化する。認証方式は、本人がパスワードを新たに管理しなくてよい**メールの6桁コード（Email OTP）**だけを採用する。

マジックリンクは採用しない。リンク方式は自前のメール事業者が必須であり、事業者を1社増やすと保存国、再委託先、保持期間、削除条件の確認がまるごと増えるためである。パスワードを管理させないという利点はEmail OTPでも同じであり、スマートフォンではメールアプリとブラウザを往復しない分だけ操作が単純になる。

初期構成では次を無効にする。

- パスワードログイン
- Google、Microsoft等のSNSログイン
- 組織機能
- 管理者による利用者代理ログイン
- 認証イベントをマーケティングや匿名分析へ送るWebhook
- **新規登録**。運営者が登録した参加者だけがログインできる状態にする

パスキーは初期方式にせず、Email OTPでの回復経路と実機利用性を保ったまま追加検証する。

### 5.2 必須要件

- 6桁コードは1回限り、短時間で失効し、要求回数と入力試行回数をメールアドレスとIP単位で制限する。
- ログイン成功時に過去の同一利用者セッションを一覧表示・個別失効できるようにする。
- クラウド有効化、全件削除、退会、メール変更は直近10分以内の再認証を要求する。
- Cookieは`Secure`、`HttpOnly`、適切な`SameSite`を必須とする。
- メールアドレス、コード、Cookie、JWTをアプリログへ出さない。
- アカウント回復は認証メールだけで行い、運営者が本人記録の内容を尋ねて本人確認しない。

### 5.3 メール送信

- 検証中は、Managed Better Authの既定である共有SMTP（`auth@mail.myneon.app`）を使う。これは開発・検証用の位置づけである。
- 公開前に、参加者が実際に使うメール事業者へ確実に届くか、迷惑メールへ振り分けられないかを実機で確認する。
- 到達性が足りない場合は、公開の条件として自前のメール事業者を追加する。その場合は保存期間、再委託先、国外取扱い、削除条件を契約前に確認する。

## 6. アクセス制御

### 6.1 API境界

```text
ブラウザ
  -> Next.js本人記録API
    -> Managed Better Authセッション検証
      -> 入力スキーマ検証（既存の parseExportPayload と同じ上限・スキーマ）
        -> 暗号化・復号
          -> RLSを有効にした本人記録DB
```

本人記録APIは、リクエストCookieから検証したユーザーIDだけを所有者IDとして使う。本文、URL、フォームから所有者IDを受け取らない。

APIは次の4つに限定する。

| API | 役割 |
| --- | --- |
| アップロード | スナップショットを1件保存し、直前の世代を退避する |
| ダウンロード | 最新スナップショットと、その保存時刻・件数を返す |
| 端末引き継ぎ | 復元した端末を「同期する端末」として登録し、以前の端末を停止状態にする |
| 削除 | クラウド上の本人データを削除する（クラウド停止・退会の両方で使う） |

### 6.2 DB権限

- マイグレーション用DBロールと実行時DBロールを分離する。
- 実行時ロールには本人記録テーブルの必要な`SELECT`、`INSERT`、`UPDATE`、`DELETE`だけを与える。
- 本人記録テーブルでRLSと`FORCE ROW LEVEL SECURITY`を有効にする。
- 1リクエストのトランザクション内で、検証済みJWTクレームを設定してからSQLを実行する。
- 本番アプリへRLSを迂回できる所有者・管理者DB資格情報を渡さない。
- 運営者向けに本人記録を検索・一覧・閲覧する画面やAPIを作らない。

障害対応で本番アクセスが必要な場合は、時間制限、理由、記録を必須にする。

## 7. 暗号化と鍵管理

### 7.1 通信・基盤

- ブラウザとVercel、VercelとNeonの通信はTLSを必須とする。
- Neonの保存時暗号化とバックアップ暗号化を利用する。
- スナップショットは、DBへ渡す前にアプリケーションでも暗号化する。

### 7.2 アプリケーション暗号化

- 利用者ごとに256bitのデータ暗号鍵（DEK）を1本生成する。
- スナップショット全体を、DEKとAES-256-GCMで暗号化する。
- AADに、所有者ID、オブジェクト種別、スキーマ版、世代番号を含める。
- DEKは、Vercelの Sensitive Environment Variables に置いた親鍵（KEK）で暗号化してDBへ保存する。
- DBには暗号文、nonce、アルゴリズム、鍵版、暗号化済みDEKだけを保存する。
- 平文DEKは1リクエスト内だけで使用し、ログ、キャッシュ、DB、エラー監視へ出さない。
- 鍵の取得・復号は1つの関数へ集約し、将来AWS KMSへ差し替える場合にその関数だけの変更で済む形にする。
- 親鍵には版番号を持たせ、入れ替え時に旧版で復号・新版で再暗号化できるようにする。

平文で保持する索引は、所有者ID、世代番号、スキーマ版、記録件数、作成・更新時刻、同期端末の識別子に限定する。気分、睡眠、服薬、しんどさのサイン、メモ、セルフケア名、記録対象日は暗号文に含める。

### 7.3 世代の保持

上書き保存で壊れた内容が唯一の控えになることを防ぐため、直近3世代のスナップショットを保持し、古い世代から削除する。世代も同じ方式で暗号化する。

## 8. 保存期間、バックアップ、削除

### 8.1 保存期間

- クラウド保存が有効なアカウントは、本人が削除するまで保存する。
- 未利用アカウントの自動削除は実装しない。
- 検証終了日を参加説明へ明記し、その日に運営者がクラウド上の本人データを全件削除する。
- 本人がアプリ内で最終預け日時を確認できるようにする。

### 8.2 本人操作による削除

- クラウド保存の停止時に「クラウド上のデータも削除する」を選べるようにする。削除は再認証後に実行する。
- クラウド全件削除は、スナップショット、世代、同期端末の登録、暗号化DEKを削除する。
- 退会は全セッション失効、本人記録削除、認証アカウント削除の順に行う。
- APIは削除要求を冪等にし、再実行しても成功として扱う。
- ライブDBからは24時間以内、通常は同一処理内で削除する。
- バックアップ内の暗号化済みデータが一定期間残る可能性を本人へ説明し、期限後に復元不能となることを運用確認する。
- 端末内のデータは削除しない。クラウドを消しても本人の手元の記録は残る。

### 8.3 バックアップと復元

- 本番前に、利用プランの時点復元期間と内部バックアップ保持期間を公式仕様で再確認する。
- 本人記録用DBのバックアップを匿名分析DBと混ぜない。
- 削除要求の記録を、本文、メールアドレス、生のユーザーIDを含めない最小限の運用記録として保持する。

## 9. 端末内データの移行、復元、1台運用

### 9.1 初回アップロード

1. 既存の`parseExportPayload`と同じ上限・スキーマで端末データを検証する。
2. 移行前に本人がJSONバックアップを取得できる導線を表示する。
3. 対象件数とデータ境界を本人へ表示し、明示確認後だけアップロードする。
4. APIで全体を検証して暗号化し、単一トランザクションで保存する。
5. 保存件数とチェックサムを照合してから、最終預け日時を更新する。
6. 成功後も端末データを自動削除しない。

タイムアウト、通信断、容量超過、検証失敗が起きた場合は、端末データを維持して再実行可能にする。途中までのアップロードをクラウドに残さない。

### 9.2 継続バックアップ

- 記録の保存が成功したら、その直後にスナップショット全体を送信する。
- 端末保存の成功とクラウド送信の成功を別の状態として扱う。記録の保存は従来どおり常に成功として表示する。
- 送信失敗は画面へエラーを出さず、次の保存時とアプリ起動時に自動で再送する。
- 画面には最終預け日時だけを表示する。一定日数以上預けられていない場合に限り、責めない表現で知らせる。

### 9.3 復元と衝突

- 復元は本人の明示操作でのみ行う。
- 端末にもクラウドにも記録がある場合、自動統合も自動置き換えもしない。件数と期間を並べて示し、「クラウドの内容で置き換える」か「この端末を残してクラウドを上書きする」を本人が選ぶ。
- どちらを選ぶ場合も、決める前にJSONバックアップの保存を必須にする。
- 復元が完了した端末を「同期する端末」として登録する。

### 9.4 1台運用

- 同期する端末は1アカウントにつき1台とする。
- 新しい端末が同期端末になると、以前の端末は次回の送信時に停止状態となり、引き継いだ日付を添えた案内を表示する。
- 停止状態の端末でも記録の作成・閲覧は従来どおり続けられる。端末内のデータは削除しない。
- 停止状態の端末で本人が希望した場合は、9.3の手順を経てその端末を同期端末へ戻せる。

## 10. ログ、監視、インシデント対応

- APIログはリクエストID、操作種別、HTTP状態、処理時間、件数だけに限定する。
- 本文、暗号文、メール、Cookie、JWT、所有者ID、記録対象日をログやエラー監視へ送らない。
- 認証失敗、RLS拒否、異常な大量取得、削除失敗、復号失敗を個人内容なしで検知する。
- 漏えい等が疑われる場合の封じ込め、鍵・資格情報の失効、影響範囲確認、本人通知・関係機関報告の判断責任者を本番前に決める。
- インシデント時も本人記録を診断、危機判定、常時監視へ転用しない。

## 11. 実装開始前と公開前の条件

### 11.1 実装してよい範囲

次はいつでも着手してよい。すべてフラグOFF・本番画面から到達不可、ダミーデータのみで行う。

| 範囲 | 状況 |
| --- | --- |
| 本人記録用のテーブル定義とマイグレーション | 実装済み（`db/migrations/0002_user_data_snapshots.sql`、`pnpm db:user-data:setup`） |
| スナップショットの暗号化・復号・親鍵の入れ替え | 実装済み（`src/lib/server/user-data-crypto.ts`） |
| 保存・取り出し・削除・端末登録のAPI | 実装済み（`src/app/api/cloud/`） |
| 端末側の送信・取り出し・復元の判断 | 実装済み（`src/lib/cloud-sync.ts`、`src/lib/cloud-sync-state.ts`） |
| Managed Better Authの有効化とセッション検証 | 実装済み（`src/lib/server/neon-auth.ts`、`src/lib/server/cloud-session.ts`、`src/app/api/auth/[...path]/route.ts`）。ログイン確認用の最小画面も実装済み（`src/app/cloud-login/`、フラグOFFのあいだは404） |
| クラウド保存の設定画面と復元画面 | 実装済み（`src/components/shared/cloud-backup-panel.tsx`、`src/components/shared/cloud-restore-dialog.tsx`）。記録タブ内のカードとして出し、フラグOFFのあいだは何も描画しない |

`NEXT_PUBLIC_CLOUD_BACKUP_ENABLED` が `true` でない限り、APIは存在しない扱い（404）で応え、DBへ接続しない。Preview環境でダミーデータを通す場合だけ、`USER_DATA_DEV_OWNER_ID` で所有者IDを固定できる。この抜け道は `VERCEL_ENV=production` では無視する。

#### 新規登録の抑止について（2026-09-08、実装時に確認）

Managed Better Authの認証フローの公式ドキュメントは次のように明記しており、Console設定だけで新規登録を確実に止められる保証が無い（本節の設計当初の想定と食い違う）。

> "Anyone can sign up for your application by default. Support for restricted signups is coming soon."

このため、Console側の設定に加えて、`getCloudSession` がアプリ側でも `USER_DATA_ALLOWED_EMAILS`（運営者が用意した参加者のメールアドレス一覧）と突き合わせる二重の防御を実装した。一覧が未設定のときは誰もログインできない（フェイルクローズ）。Console側の新規登録抑止設定が実際に効くかどうかは別途確認が要る（`docs/handoff/latest.md` 参照）。

#### 削除前の再認証について（2026-09-09、設定画面の実装時に確認）

4節と8.2節は、クラウド停止と退会の削除を再認証後に実行すると定めている。`isRecentlyVerified` は当初から用意されていたが、どのAPIからも呼ばれていなかった。設定画面から削除を実行できるようにするにあたり、`DELETE /api/cloud/snapshot` で直近の本人確認（既定10分）を必須にし、古い場合は削除せず `403`（`reason: "reauth_required"`）を返す形に改めた。画面はこの応答を受けたときだけ、もう一度ログインする導線を出す。

判定は `src/lib/server/cloud-reauth.ts` に切り出した。認証基盤（`neon-auth.ts`）を読み込まない純粋な関数にしてあるため、テストでセッション取得を差し替えても、この守り自体は差し替わらない。

#### 退会時の認証アカウント削除は未実装（2026-09-09時点）

8.2節は退会を「全セッション失効、本人記録削除、認証アカウント削除の順」と定めている。現状の実装は、クラウド上の本人データ削除とサインアウト（セッション失効）までで、**認証アカウントそのものの削除は行っていない**。Managed Better AuthのSDKには `delete-user` の経路が存在するが、better-auth本体ではサーバー側で明示的に有効化する必要がある設定であり、Managed Better AuthではNeon側がホストしているため、アプリのコードから有効化できるかを今回の調査では確認できなかった。ベータの記載と実装が食い違う可能性があるため、動作を確かめずに呼び出すことはしていない。公開の入口を開ける前に、Console上またはSDKで認証アカウントを削除できるかを確認し、できない場合は運営者が手作業で削除する手順を決める必要がある。

### 11.2 公開の入口を開ける条件

次をすべて満たすまで、本番画面からクラウド保存へ到達できるようにしない。

- 現在の5か月間プログラムへ適用する場合の説明・同意・研究・安全管理手続き確認が完了する
- Neonの契約、保存国、再委託先、保持期間、削除条件を確認する
- Managed Better AuthのGA状況を再確認し、ベータのまま公開してよいかを判断する
- 参加者が使うメール事業者へ6桁コードが確実に届くことを実機で確認する。届かない場合は自前のメール事業者を追加し、その契約条件も確認する
- 本人向けプライバシー説明と同意画面がレビュー済みである
- 検証終了日と、その日に全件削除する手順が決まっている
- 親鍵の入れ替え手順が文書化されている
- 12節の検証項目がすべて通っている

## 12. 検証項目

検証はダミーデータ専用のPreview環境で行う。実データや現在の端末記録を使わない。

1. 未認証、期限切れ、改ざんCookieを拒否する。
2. 利用者Aのデータを利用者Bから読み書きできないことを、APIとRLSの両方で確認する。
3. 所有者IDを本文から指定・変更できないことを確認する。
4. 正常な暗号化・復号、異なる鍵、AAD改ざん、nonce改ざん、親鍵の入れ替えをテストする。
5. ログとエラー監視に本文・認証情報が含まれないことを確認する。
6. 初回アップロードの成功、破損、上限超過、通信断、再実行をテストする。
7. 端末にもクラウドにも記録がある状態での復元で、選択前にJSONバックアップが必須になることを確認する。
8. 復元で端末が切り替わったとき、以前の端末が停止状態になり、端末内データが消えないことを確認する。
9. 送信失敗が記録保存の失敗として表示されないこと、再送で回復することを確認する。
10. クラウド停止、全件削除、退会、再実行をテストする。
11. スマートフォンで6桁コードの受信・入力、再認証、最終預け日時の表示、失敗時の復旧をタスクテストする。
12. 新規登録を無効にした状態で、登録していないメールアドレスからログインできないことを確認する。

## 13. 採用しない構成

| 構成 | 採用しない理由 |
| --- | --- |
| 複数端末の継続同期と競合解決 | 実装量とデータ喪失リスクの大半を占め、現在の利用実態で必要性を確認できていないため |
| 匿名分析用Neonへの本人記録追加 | 匿名イベントと本人記録のデータ境界、資格情報、削除、権限を分離できないため |
| ブラウザからNeon Data APIへ直接CRUD | 入力検証、暗号化、レート制御、ログ抑制をNext.js APIへ集約するため |
| 全利用者で共通の単一暗号鍵 | 利用者別DEK、鍵の用途制限、入れ替えを弱めるため |
| 独自パスワード認証 | パスワード保管、リセット、攻撃対策をアプリ側で持たないため |
| メールのマジックリンク | 自前のメール事業者が必須となり、保存国・再委託先・保持期間の確認先が1社増えるため。パスワードを管理させない利点はEmail OTPで得られる |
| 最終更新時刻だけのLast Write Wins | 複数端末で本人の記録を気付かず失う可能性があるため |
| 未利用アカウントの自動削除 | 誤動作時に本人の記録を取り返しのつかない形で消すため。数名規模では運用で代替できる |
| 手続き確認前の本番公開 | 現行の参加説明の範囲を変えるため |

## 14. 未決事項

| 未決事項 | 決める内容 |
| --- | --- |
| 同意文面と手続き確認 | 誰に、いつまでに確認を取るか。確認が済むまで入口を開けない |
| 1台運用の文面 | 停止状態になった端末に表示する案内の文言 |

| ベータのGA状況 | 公開前にManaged Better AuthがGAへ移行したかを再確認する |

## 15. 意思決定記録

| 日付 | 決定 | 理由 |
| --- | --- | --- |
| 2026-07-26 | 複数端末同期を含むフル構成を確定し、本番実装はGate 3まで保留する | 需要が未確認のまま高コスト・高リスクな投資を行わないため |
| 2026-09-08 | バックアップと復元だけの最小構成へ縮小し、フラグOFFのまま実装に着手できるようにする | 投資額とデータ喪失リスクの大半を占める同期の競合処理を外し、既存のJSONバックアップの仕組みを再利用できるため |
| 2026-09-08 | ログイン方式をマジックリンクからEmail OTP（6桁コード）へ変更する | リンク方式は自前のメール事業者が必須と公式に明記されており、事業者を1社増やすと確認先と手続きの重さが増すため |
| 2026-09-08 | 新規登録の抑止をConsole設定だけに委ねず、アプリ側（`getCloudSession`）でも許可済みメールアドレス一覧との突き合わせを行う | 公式ドキュメントが新規登録の制限を「近日対応」と明記しており、Console設定だけで確実に止められる保証がないため |
| 2026-09-09 | 停止・退会の削除APIで直近の本人確認（10分）を必須にし、古い場合は削除せず再ログインを求める | 4節・8.2節が定める「削除は再認証後」がどのAPIでも実施されておらず、古いCookieが残っているだけで消せる状態だったため |
| 2026-09-09 | 復元の導線を、記録が1件も無い端末（機種変更の直後）にも出す | 機種変更で記録を失った人が預けた控えへたどり着けないと、この機能の目的そのものが果たせないため |
| 2026-09-09 | 「この端末の内容をクラウドに預ける」を本人が押した時点を、アップロードの明示同意として扱う | 件数を示したうえでの操作であり、4節が求める「明示確認の後だけアップロードする」を満たすため。ログインだけでは同意にならない点は変えていない |
