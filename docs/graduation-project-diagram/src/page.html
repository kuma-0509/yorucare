AI-DRIVEN SCHOOL ／ 第1期 土曜クラス ／ 6ヶ月目 卒業制作

ヨルケア

支援が届かない夜と休日に、自分の状態を
1〜2分だけ残せるようにした。

メンタル不調から復職したあと、平日の夜と土日祝に調子が落ちる。けれど支援は平日の日中にしかない。その空白の時間に、スマートフォンだけで完結する「本人のためのセルフケア記録」を作りました。

yorucare.vercel.app ↗ Next.js 15 ／ TypeScript ／ Tailwind CSS 記録は端末内だけに保存

この図解に載せた画面は、すべて検証用のダミーデータで撮影しています。実在の体調・服薬・面談の内容、氏名、所属は含みません。ヒアリングの内容も一般化して記載しています。

01 ／ WHAT I BUILT

作ったもの

スマートフォンのブラウザで開く、セルフケア記録のWEBアプリです。ログインもインストールも要りません。開いた瞬間に「よい／ふつう／しんどい」の3つが並び、1つ押して保存すればその日の記録は終わりです。書けることがある日だけ、睡眠・メモ・できたこと・明日の小さな目標を足せます。

TAB 01

書く

3段階を選んで保存。追加の項目は本人が選んだものだけ出る。

TAB 02

これまで

直近7日の記録。あとから直せる。ファイルへの保存と復元もここ。

TAB 03

できること

自分に効いた行動の登録簿。記録画面から1タップで選べる。

TAB 04

ふりかえり

積み重ね・週のまとめ・体調の傾向グラフ。評価も助言もしない。

実際の画面

iPhone相当（390×844）で撮影。内容はすべてダミーデータ。

02 ／ THE PROBLEM

解決する面倒・課題

面倒①　支援が動いていない時間に、調子が落ちる

通勤も業務も、緊張感でなんとか乗り切れる。落ちるのは帰宅後の夜と、土日祝です。ところが職場も産業医も支援機関も平日の日中に動いていて、通院と支援面談は月1回。いちばん揺れる時間帯に、相談できる相手がいません。「週末で回復させても、月曜が怖い」が繰り返され、再休職の入口になります。

面倒②　体調記録は、続かないほうが普通だった

支援員へのヒアリングで繰り返し出てきたのが「復職して1〜2ヶ月で体調管理の記録が途切れ、そこから不調が出る」という話でした。当事者は自作の表計算ファイルで、ひとりで管理している。既存のアプリは服薬に特化したものが多く、体調の波と生活リズムまでを一体で扱えるものが見当たりませんでした。

理由は根性ではなく設計です。項目が多いほど「今日は書けない」が起き、空白が並ぶと自分を責め、開かなくなる。だから最初に決めたのは「保存の最低条件を、状態1つに下げる」ことでした。

HEARING 01

夜のSNS閲覧が習慣になり、睡眠不足がそのまま翌日の不調になる。

HEARING 02

会社には相談しにくい。支援面談は月1回。表計算ファイルでひとりで管理している。

HEARING 03

面談は仕事ができているかの確認で精一杯で、生活や体調まで踏み込む時間がない。

復職経験者・就労移行支援の支援員へのヒアリングで確認した内容を、個人が特定されない形に一般化して記載。

03 ／ WHY I MADE IT

作りたいと思った理由

もともと、就労移行支援の事業所へ運動講座を届ける仕事をしています。現場に入るたびに聞こえてくるのが、決まって「夜と休日の話」でした。日中は動けている人が、帰宅後と週末に崩れる。けれど支援は平日の日中にしかない。

その空白を埋めようと、平日夜と日曜のオンラインセッションを始めました。すると次の面倒が出てきます。セッションに来ていない日の状態が、誰にも分からない。本人も「先週どうでしたか」に答えられない。支援員との月1回の面談も、思い出せる範囲の話から始まる。

つまり、足りないのは支援の熱量ではなく「本人の手元に残る、その日の記録」でした。表計算ファイルで孤独に管理するのをやめたい。面談を「今日どうでした？」から始めるのをやめたい。この2つの面倒は、自分の仕事のなかで毎週感じているものだったので、卒業制作のお題にしました。

同時に、はっきり決めたことがあります。診断も治療もしない。体調を判定せず、助言もせず、良し悪しを言わない。医療と福祉の代わりではなく、その手が届かない時間帯を埋める道具に徹する。この線を最初に引いたことが、そのあとの実装判断のほぼすべてを決めました。

DESIGN CONSTRAINTS

先に引いた4本の線

  • 診断・治療・危機判定をしない
    状態から危険度を推定しない。
  • 記録の本文を端末の外へ出さない
    運用ルールではなく、型と経路で保証する。
  • 評価語・助言を画面に出さない
    「すごい」「順調」「改善」を出さないことをテストで固定する。
  • 書けなかった日を失敗として描かない
    連続日数を主役にせず、累計を先に置く。

04 ／ HOW

どう作ったか

課題で案内された4ステップの順に進めました。ここは実際に踏んだ順序なので、番号どおりです。

  1. 01

    毎日の面倒を書き出して、お題を決める

    「夜と休日に支援がない」「記録が続かない」「面談が思い出し話から始まる」を分解し、いちばん手前にある“記録が続かない”をお題にした。

  2. 02

    grill-me で企画を詰める

    「誰がどれくらい困っているのか」を問われ続けたことで、対象を“復職後に波が残る人”へ絞り、診断・治療をしないという線が固まった。ここで決めた境界を、あとから docs/ の判断メモ20本に残した。

  3. 03

    企画をもとに作り上げる

    Tailwind CSS で画面のモックアップ → Next.js で動く形 → 自分のスマートフォンで毎日使う → Vercel で公開、の順。作っては使い、直しては使うを125回のコミットに分けて回した。

  4. 04

    発表資料を作り、練習する

    聞き手は自分の仕事を知らない前提で、「何を作ったか」より先に「なぜ作ったか」を置いた構成にした。この図解も同じ順序で並べている。

いちばん効いた構造：差し替えられる継ぎ目を1か所にする

記録は今、端末のブラウザの中にしかありません。将来クラウドへ移すかどうかは、まだ決めていません（後述のゲートで判断します）。決めていないものを作らずに済ませるために、画面からデータへ触る経路を repository.ts の1か所に集約しました。移すと決めた日に、差し替えるのはここだけです。

05 ／ WHAT I GOT RIGHT

工夫したポイント

扱うのが体調の記録なので、「気をつけて運用する」では守れないものがあります。運用ルールではなく、破れない形にできたかどうかで判断しました。

A.　外へ出ない、を型と経路で保証する

記録の本文は端末の外に出しません。これを「送らないように気をつける」で終わらせず、送る経路そのものを作らないことにしました。ブラウザの通信先は自分自身に限定してあり、外部サービスへ渡す実装が存在しません。共有したいときは、本人が全文を確認したうえで、ファイル保存かコピーで自分の手で渡します。

B.　AIに文章を書かせず、候補から選ばせる

面談や通院の前に持っていける「期間の報告書」を作る機能で、いちばん悩んだところです。最初はAIに文章を書かせて、診断や助言に読める言葉を禁止語リストで弾く形を考えました。

でもこれは担保になりません。一覧に挙げていない言い回しは、そのまま通ってしまうからです。禁止語を足し続けても、書かれ得る文のほうが必ず多い。そこで方式ごと変えました。数値はアプリが確定させ、文章はアプリが用意した候補から1つ選ばせる。渡していない主張が報告書に入る経路が、そもそも無くなります。

C.　「作らない条件」を、作る前に決めておく

リマインド通知、アカウント、クラウド保存、共有リンク。どれも「あったほうがいい」機能ですが、どれも個人の健康情報を扱う責任と固定費が増えます。そこで、着手する前に「何が観測できたら作るか」を5つのゲートとして先に決め、満たすまで実装しないことにしました。

結果として、いま保留にしている機能が3つあります。作れなかったのではなく、まだ作らないと決めている状態です。

D

言葉を1か所に集めた

画面に出る文言は copy.ts だけを見れば分かる形にしました。「できること」と「できたこと」のような紛らわしい語を1語に決め、localStorage や JSON といった技術用語は当事者向けの画面に出しません。文言を直書きした箇所が見つかるたび、ここへ戻しました。

E

評価語を出さないことをテストで固定

「すごい」「順調」「改善」のような評価語と助言を、節目のねぎらい文にも週のまとめにも出しません。人がうっかり足せてしまうので、禁止語の一覧を1か所に置き、表示テストで落ちるようにしました。割合ではなく日数で示し、数値には必ず母数を添えます。

F

オープンデータで地域の相談先へ

東京都のオープンデータから、特別区・市町村・中核市の保健所と保健センター163か所（58区市町村）を統合しました。選んだ地域は保存も送信もせず、現在地も取得しません。電話も公式サイトも、本人が押したときだけ開きます。

06 ／ WHAT WENT WRONG

苦戦したポイント

うまくいった話より、こちらのほうが学びが多く残りました。5つとも「作ってから気づいた」ことです。

CASE 01

3週間かけた演出を、実機テストの結果ぜんぶ消した

何が起きたか

記録を保存したあとに、書いた紙が本になって書庫にしまわれる3Dの演出を作りました。革・紙・木の質感、カメラの動き、音、縦長画面での見切れまで詰めて、いちばん時間をかけた部分です。

どう直したか

実機で触ってもらった結果は「毎日やるには要らない」。保存したらすぐ完了画面へ戻る形に戻し、3D一式・音の設定・関連するテストと依存関係まで削除しました。1〜2分で終わるという約束と、7秒の演出は両立しません。作り込みの量ではなく、目的に合うかで判断すると決め直しました。

CASE 02

項目を増やすほど、書けなくなった

何が起きたか

自分メンテ、しんどさのサイン、小さな目標。役に立つ機能を足すたび、記録画面が縦に伸びました。自分で毎日使っていて、開いた瞬間に閉じたくなる日が出てきました。

どう直したか

追加した5項目を、端末内の設定で表示・非表示にできるようにし、既定をすべて非表示にしました。いつも出るのは日付・状態・睡眠・メモだけ。非表示にしても保存済みの記録は消えず、戻せばまた見えます。機能を消さずに、初期状態だけを軽くする形に落ち着きました。

CASE 03

指標の分母を間違えると、都合のいい数字が出る

何が起きたか

「中断後の再開率」を集計したら、必ず100%になりました。再開した人だけを分母に入れていたからです。さらに、観測期間の途中で数えると、その日のうちに届いた保存で報告済みの値があとから変わることにも気づきました。

どう直したか

戻らなかった側も分母に数え、観測窓（Day 0〜Day 27）が終わってから初めて集計対象に入れる形にしました。割合には必ず母数を添え、母数が0のときは値を出さない。自分の作ったものを評価する数字ほど、疑ってかかる必要がありました。

CASE 04

「消したはず」の記録が、端末に残っていた

何が起きたか

記録を削除しても、演出の履歴が別のキーに残っていました。中身は消えていても、どの日に記録したかという日付の一覧が端末に残る。共有のパソコンで使い終わった人にとっては、これも十分に個人的な情報です。

どう直したか

1件の削除でも全件削除でも、関連する履歴を先に消してから本体を消すようにし、履歴の削除に失敗したら本体も消さない形にしました。削除は「見えなくする」ではなく「残らない」まで持っていく必要がある、と学びました。

CASE 05

テストの手順そのものが、測定になっていなかった

何が起きたか

「補助なしで2分以内に記録できるか」を測るはずの手順書に、押すボタンの位置が書いてありました。これでは、迷う場所こそ見つけたいのに、迷いが起きません。あわせて、日本時間で走らせると落ちるテストも見つかりました（世界標準時のつもりで日付を計算していた）。

どう直したか

参加者に渡す「操作を教えない指示」と、実施者用のチェックリストを分け、無誘導の計測を先に行う順序にしました。日付の計算は、製品と同じ集計経路を通して検証する形へ直しました。測りたいものが測れる手順かを、実施前に点検する必要があります。

08 ／ NEXT

これから

STEP 1

実機テストを終える

iPhone と Android で、5人に無誘導で触ってもらう。「補助なしで2分以内に保存できるか」「週の状態を振り返る場所へ到達できるか」を測る。手順書はもう直してある。

STEP 2

Gate 1 を判定する

15台・4週間の観測で、初週に複数日書けた割合と2週目・4週目の継続を見る。ここで継続の兆しが出なければ、リマインドもクラウド保存も作らない。

STEP 3

実践研究につなげる

約20名規模で、夜間・休日のオンラインセッションと記録を組み合わせて検証する。指標案は PHQ-9・UWES-9・WHO-HPQ・PSQI。効果が確かめられてから、広げる。

半年間で身についたのは、作る速さより「作らない判断を、根拠つきで残す書き方」でした。夜と休日の空白は、まだ埋まっていません。小さく作って、使って、直す。それを続けられる形にできたことが、この卒業制作でいちばんの成果です。
